# GEOFlow 客户交付工作流

## 适用范围

用于把 GEOFlow 的真实产品能力转化为客户方案、传播执行规划、内容生产简报、交付清单或阶段复盘。它不代替品牌、营销、公关和内容策略，也不授权直接操作线上系统。

## 第一步：确认客户问题

记录业务目标、目标受众、现有内容与站点、AI 搜索平台、发布渠道、团队、预算、周期、审批流程、合规要求和期望结果。把“希望获得更多曝光”改写为可以验证的问题，例如内容生产慢、事实不统一、分发不可追踪、人工发布缺少责任人或 AI 引用表现无法持续监测。

## 第二步：建立能力证据表

按目标实例逐项标记：

| 状态 | 含义 |
| --- | --- |
| 已验证 | 已由代码、CLI 帮助、路由、后台页面或读回结果确认 |
| 可配置 | 系统支持，但目标实例尚未完成配置或授权 |
| 需开发 | 当前实例没有，需要单独估算和验收 |
| 不承诺 | 受平台、内容质量、外部审批或市场因素影响，系统无法保证 |

不得把公开版本中的功能直接写成客户实例已经具备。涉及 CLI 0.2.0、人工发布、企业知识库、主题、线索、分发、数据分析或安全审计时，均需现场核验。

## 第三步：设计交付链路

按实际需要组合，不要默认全量销售：

1. 资料治理：来源收集、企业知识库草稿、待确认项、版本与审批。
2. 内容生产：关键词或标题库、任务、知识库绑定、文章草稿、人工复核与风险扫描。
3. 站点承接：主题、首页模块、SEO 元数据、结构化内容、线索表单与转化路径。
4. 渠道分发：本地发布、目标站点、WordPress、通用 API 或经核验的渠道能力。
5. 人工发布：工单、身份与账号、执行人、排期、重复提醒、结果地址和状态历史。
6. 效果复盘：内容、访问、AI 可见性、来源、线索和分发日志；明确哪些指标只是过程信号。

每个环节写清输入、动作、负责人、审批人、系统记录、输出、指标、异常处理和不在范围内的事项。

## 第四步：形成客户方案

建议结构：

1. 客户现状与关键判断。
2. 本阶段目标和不承诺事项。
3. 已验证能力、需配置能力与需开发能力。
4. 端到端工作流和客户参与点。
5. 分阶段交付物、负责人、依赖和验收标准。
6. 周期、资源、预算口径和变更机制。
7. 指标、数据来源、复盘节奏和停止条件。
8. 权限、隐私、平台合规、人工审核和发布风险。

方案不得承诺 AI 平台必然引用、关键词必然排名、内容必然收录、媒体必然发布或线索必然成交。

## 第五步：传播与文案协作

- 对外介绍系统时，只写经核验的能力、适用条件和客户价值，不把产品路线图写成已上线功能。
- 产品发布、新闻稿和公共文案交给 `$pr-strategy-workbench` 建立事实底稿与审批链。
- 客户营销方案和获客路径交给 `$wepr-marketing`。
- 文章、案例、渠道内容和产品说明交给 `$create-marketing-content`。
- 最终中文润色交给 `$wepr-human-writing`，不得改变功能边界、报价、承诺和安全说明。
- 需要写入 GEOFlow 时，先完成内容审批，再切换至 `operations`，执行预检、最小权限操作与读回验证。

## 验收清单

- 每项产品能力都有目标实例证据。
- 方案里的服务范围与系统动作一一对应。
- 人工动作、自动化动作和外部平台动作已分开。
- 负责人、审批人、指标口径、时间和异常处理明确。
- 内容事实、客户数据和账号权限有来源与保护措施。
- 没有把系统输出、发布动作或过程指标写成业务结果保证。
